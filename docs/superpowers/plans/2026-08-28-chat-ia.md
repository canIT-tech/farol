# Chat IA (tool-calling) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `POST /trips/:id/chat { message }` — o Claude, num loop de tool-calling, altera o estado da viagem chamando ferramentas mapeadas 1:1 para métodos de serviço (trocar destino, mudar datas, regenerar dia, remover/fixar item, achar hotel, trocar restaurante, buscar voos, ajustar perfil). O estado da viagem no Postgres é a fonte da verdade; a resposta devolve o `TripState` atualizado + o texto do assistente. Mensagens ficam em `chat_messages`.

**Architecture:** `LlmService.runToolLoop` roda o ciclo do Anthropic tool-use: manda a mensagem + as definições de tool → recebe blocos `tool_use` → o `ToolRouter` executa cada um contra os serviços reais → devolve `tool_result` → repete até `end_turn` (ou limite de passos). `ChatModule` persiste as mensagens (`user`, `tool`, `assistant`), aplica guard-rails (throttle por usuário, teto de passos/tokens, timeout por tool) e relê o `TripState` no fim. `FakeLlmService` roda um roteiro de tool-calls determinístico por chave de mensagem.

**Tech Stack:** herda dos Planos 1–6. Sem dependência nova.

**Spec:** `docs/superpowers/specs/2026-08-27-mvp-trip-design.md` §5.1 (`chat_messages`), §6.4 (chat + 9 tools + fonte da verdade + undo por versão), §10 (rate limiting no chat). Telas: `Itinerary.dc.html` (trilho), `AutoPlan.dc.html`.

## Global Constraints

- Herdam dos Planos 1–6 (pnpm, Node 22, cobertura 100% por pacote, mutação ≥ 90%, TDD, `@farol/*`, env com zod, PT-BR, DoD = testes completos).
- **Estado no Postgres é a fonte da verdade.** As tools só disparam mutações via serviços já existentes (Planos 3–6). A resposta relê o `TripState`; nunca serializa "estado do chat".
- **Uma tool = um método de serviço.** Nada de lógica de negócio no `ToolRouter` além de validar o input (zod) e chamar o serviço.
- **Autorização:** toda tool recebe `userId` do `@CurrentUser` e o repassa ao serviço, que já valida dono.
- **Guard-rails:** `CHAT_MAX_STEPS` (default 6) passos de tool por turno; `CHAT_MAX_TOKENS` no `messages.create`; timeout por tool (`CHAT_TOOL_TIMEOUT_MS`, default 15000); throttle `@nestjs/throttler` só nesta rota (`CHAT_RATE` req/min por usuário).
- **LLM em teste = fake determinístico:** `FakeLlmService.runToolLoop` executa uma sequência de tool-calls fixada por "kind" da mensagem do usuário, e devolve um texto de assistente fixo.
- **Undo:** regenerações completas já criam `version` nova (Passo 4). Mutações pontuais (`remove_item`, `pin_item`) **não têm undo** no MVP — anotado; `chat_messages` guarda o histórico para auditoria.

### Task 4: `apps/api` — `ToolRouter` (nome da tool → serviço)

**Files:**
- Create: `apps/api/src/chat/tool-router.ts`, `apps/api/src/chat/tool-router.types.ts`
- Test: `apps/api/src/chat/tool-router.spec.ts` (integração — serviços reais com Postgres, `FakeLlmService` onde precisar)

**Interfaces:**
- Consumes: `TripsService`, `ItineraryService`, `ProfileService`, `FlightsService`, `HotelsService`, `PlacesService` (Planos 3–6); `CHAT_TOOLS` (Task 2).
- Produces:
  - `ToolRouter.execute(ctx: { userId: string; tripId: string }, call: ToolCall): Promise<ToolResult>`
    - Valida `call.input` com o `inputSchema` da tool (erro de validação → `ToolResult{ isError: true, output: <mensagem> }`).
    - Mapa `name → (ctx, input) => Promise<unknown>`:
      - `set_destination` → `ItineraryService.chooseDestination(userId, tripId, iata)`
      - `shift_dates` / `set_duration` / `set_budget` → `TripsService.update(...)` (adicionar `update` ao `TripsService` — Task 4 do plano cobre)
      - `add_interest` / `remove_interest` → `ProfileService.upsert` com o array ajustado
      - `regenerate_day` → `ItineraryService.regenerateDay(userId, tripId, dayIndex)`
      - `remove_item` → `ItineraryService.removeItem(userId, tripId, itemId)` (novo)
      - `pin_item` → `ItineraryService.setPinned(userId, tripId, itemId, true)` (novo)
      - `find_hotel` → `HotelsService.search(userId, tripId)` (retorna as ofertas como `output`)
      - `swap_restaurant` → `ItineraryService.swapRestaurant(...)` (Plano 6)
      - `search_flights` → `FlightsService.search(userId, tripId)`
    - Todo erro de serviço vira `ToolResult{ isError: true, output: <code + mensagem curta> }` — o loop repassa ao modelo, não estoura o request.

- Produces:
  - `ChatService.send(userId, tripId, message): Promise<ChatResponse>`:
    1. Valida dono (`TripsService.get`).
    2. Persiste `chat_messages { role: "user", content: message }`.
    3. Carrega histórico (últimas N mensagens `user`/`assistant`).
    4. `LLM.runToolLoop({ history, message, tools: toolJsonSchemas(), executeTool: (call) => withTimeout(toolRouter.execute({ userId, tripId }, call), CHAT_TOOL_TIMEOUT_MS), maxSteps: CHAT_MAX_STEPS })`.
    5. Persiste `chat_messages { role: "tool", content: "<resumo>", toolCalls: <calls+results> }` e `{ role: "assistant", content: assistant }`.
    6. Relê `TripState` e devolve `{ assistant, tripState, steps }`.
  - `POST /trips/:id/chat { message }` → 200 `ChatResponse` | 401/403/404/429.
  - Throttler só nesta rota.
